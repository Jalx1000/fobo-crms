Resumen ejecutivo de la integración

Odontoking CRM implementa un módulo de verificación de cobertura dental que se conecta directamente a la API MedinetGo de Alianza Seguros (ambiente devnet.alianza.com.bo) para consultar en tiempo real si un paciente cuenta con beneficios dentales activos.

El sistema fue diseñado con una arquitectura de drivers intercambiables, lo que permite que el CRM soporte múltiples aseguradoras bajo el mismo flujo de usuario. El driver específico para Alianza (AlianzaDriver) realiza exactamente 2 llamadas HTTP consecutivas por cada verificación: primero autentica al proveedor y luego consulta la cobertura odontológica.

Estado actual: La integración opera sobre el ambiente de desarrollo/QA de Alianza (https://devnet.alianza.com.bo/ApiGateway). Las pruebas funcionales están completadas. Este documento se prepara para el proceso de pase a producción.
Pendiente para producción: La URL base de Alianza está actualmente configurada como variable de entorno en el servidor del CRM. Una vez que Alianza proporcione la URL del ambiente productivo, se actualiza sin cambios en el código fuente.

Endpoints consumidos en Alianza Seguros

El sistema realiza exactamente 2 llamadas HTTP consecutivas a la API de Alianza por cada verificación (cuando no hay resultado en caché).

POST https://devnet.alianza.com.bo/ApiGateway/LoginUserProv

Propósito: Autenticar al sistema CRM como proveedor autorizado. Devuelve un token de sesión (accessToken) y un código de proveedor (nUsercode) necesarios para la segunda llamada.

Payload enviado (JSON)

{
  "user":         "<ALIANZA_USER>",   // Variable de entorno - nunca en código fuente
  "password":     "<ALIANZA_PASS>",   // Variable de entorno - nunca en código fuente
  "module":       "string",
  "method":       "string",
  "nApplication": 0
}

Respuesta esperada (éxito)

{
  "success": true,
  "data": {
    "accessToken": "<JWT_TOKEN_EFIMERO>",
    "webClientVtime": [
      { "nUsercode": 12345 }
    ]
  }
}
Uso del resultado: accessToken y nUsercode son efímeros - se usan únicamente para la segunda llamada HTTP de la misma solicitud. No se persisten en base de datos ni en caché.

Seguridad y manejo de datos sensibles

Credenciales de proveedor

Las variables ALIANZA_USER y ALIANZA_PASS se almacenan exclusivamente en el archivo .env del servidor. Nunca en código fuente ni en el repositorio git.

Token de sesión efímero

El accessToken obtenido del login de Alianza es de uso único por solicitud. No se persiste en base de datos ni en caché. Se descarta tras la segunda llamada HTTP.

Audit log con hashes

La tabla insurance_audit_logs almacena únicamente hashes SHA-256 del CI, el token de API y el nombre del seguro. Nunca los valores originales en claro.

Respuestas anti-enumeración

El endpoint del agente WhatsApp (/api/v1/insurance/verify) devuelve la misma respuesta para "paciente no encontrado" y "sin seguro activo", evitando revelar si un CI existe en el sistema.

Rate limiting

El endpoint del agente externo tiene un límite de 10 verificaciones por minuto por token de API. Superado el límite devuelve HTTP 429 con el tiempo de espera.

Transporte HTTPS

Todas las llamadas a la API de Alianza se realizan sobre HTTPS. El cliente HTTP de Laravel verifica el certificado SSL del servidor de Alianza.

Manejo de errores y resiliencia

El sistema está diseñado para que ningún fallo en la API de Alianza bloquee la operación del CRM. Todos los errores son capturados y resultan en el estado INDETERMINADO, permitiendo que el operador tome una decisión manual.

Escenario de errorComportamiento del sistemaEstado resultanteImpacto en atención
Timeout en /LoginUserProv o /OdontologyCoverage Se captura Exception, se loguea con nivel error INDETERMINADO Operador puede reintentar manualmente
Alianza responde HTTP 4xx o 5xx Se detecta con $response->failed(), se loguea el body INDETERMINADO CRM no cae; atención puede continuar como particular
Alianza no disponible (DNS, red) Excepción de conexión capturada en bloque try/catch INDETERMINADO Mismo que arriba
Login exitoso pero success: false en cobertura Se evalúa messageError para clasificar EN_MORA vs NO_REGISTRADO EN_MORA / NO_REGISTRADO Operador ve mensaje descriptivo
CI vacío en el perfil del paciente El servicio rechaza antes de llamar a Alianza INDETERMINADO Se pide al operador completar el CI
Error al actualizar atributos en BD Capturado en updateInsuranceAttributes(), loguea el error pero no interrumpe la respuesta al frontend Sin cambio de estado en BD Resultado se muestra igual al operador

Log de errores

Los errores se registran usando el sistema de logging de Laravel bajo el canal por defecto. Los identificadores de log relevantes son:

[AlianzaDriver] Login fallido          → HTTP status + body de Alianza
[AlianzaDriver] Error Crítico           → mensaje de excepción + stacktrace + CI
[AlianzaDriver] Error actualizando atributos → mensaje de excepción
[InsuranceService] Verificación realizada    → person_id + status + seguro_name
[verifyForAgent] Webhook error          → mensaje de excepción (endpoint agente)

Sistema de caché

El CRM implementa caché del lado del servidor para minimizar las llamadas a la API de Alianza. Esto protege a Alianza de llamadas repetidas por el mismo paciente en un corto período.

ParámetroValorCómo configurar
TTL por defecto3600 segundos (1 hora)Variable services.insurance.cache_ttl
Habilitado por defectoSíVariable services.insurance.cache_enabled
Backend de cachéRedis o File (según configuración del servidor)Variable de entorno CACHE_DRIVER
Invalidación manualDisponible por operador en la UIBotón "Borrar Caché" en perfil del paciente

Claves de caché

// Verificación desde perfil del paciente registrado
"insurance_verify_{personId}_{md5(seguroId + '|' + ci)}"

// Verificación rápida (paciente aún no registrado en BD)
"insurance_verify_quick_{md5(seguroName + '|' + ci)}"

// Verificación desde agente WhatsApp
"insurance_verify_agent_{md5(seguroName + '|' + ci)}"
Nota para reconciliación de pruebas: Durante las pruebas QA, el cache puede deshabilitarse temporalmente configurando INSURANCE_VERIFY_CACHE_ENABLED=false en el servidor, lo que garantiza que cada verificación de prueba genere una llamada real a la API de Alianza.
