## Bug crítico: acceso incorrecto a `attendances`

El método `processDropbox()` actual accede así:

```php
// Línea 50 de IncomingAppointmentService.php — INCORRECTO
$patient = $data['attendances'][0]['patient'] ?? [];
```

Pero el schema real del JSON **no tiene una sub-clave `patient`** dentro de cada elemento de `attendances`. El paciente ES el elemento del array directamente:

```json
"attendances": [
  {
    "phone": "60000001",   // ← teléfono está aquí, no en ['patient']['phone']
    "name": "Abad",        // ← nombre está aquí, no en ['patient']['name']
    "lastName": "Rojas"
  }
]
```

El código actual siempre obtiene `$patient = []`, lo que resulta en:
- `patient_name` = `'Paciente '` (hardcodeado)
- `patient_phone` = `'0'` (hardcodeado)

**Este bug hace que NINGÚN paciente real se sincronice desde Dropbox hoy.**

La corrección es:

```php
// CORRECTO
$patient = $data['attendances'][0] ?? [];
```

## Cómo funciona la deduplicación actual

La tabla `smd_synced_events` (planificada pero aún no migrada) usa `external_id` como clave única. El comando `smd:sync-dropbox` hace:

```php
if (DB::table('smd_synced_events')->where('external_id', $externalId)->exists()) {
    $skipped++;
    continue;
}
```

Donde `$externalId` se extrae del **nombre del archivo** (`pathinfo($file['name'], PATHINFO_FILENAME)`), no del campo `_id` del JSON.

El nombre del archivo tiene el formato:
```
event-2026-05-08-0002-6a026e1d001ab20007817c40.json
```

Así que `$externalId` resulta en `event-2026-05-08-0002-6a026e1d001ab20007817c40`, no en el `_id` limpio (`6a026e1d001ab20007817c40`).

**Esto puede causar que el mismo evento se procese dos veces** si el mismo `_id` llega en un archivo con nombre diferente (p.ej., si SMD regenera el archivo con otro prefijo de fecha/hora).

## Brechas identificadas para sincronización completa

### Brecha 1 — Bug en parser de paciente (CRÍTICA)
`attendances[0]['patient']` no existe. Debe ser `attendances[0]` directamente.
Ver Tarea 5.2.

### Brecha 2 — No hay actualización (solo creación)
Si llega el mismo `_id` con `startDate` o `summary` modificado, el sistema lo ignora (deduplicación). No existe lógica de "update si el evento ya existe con datos distintos".
Ver Tarea 5.2.

### Brecha 3 — `archived: true` ignorado
Si el médico cancela una cita en SMD, SMD escribe el mismo archivo con `archived: true`. El CRM no hace nada al respecto.
Ver Tarea 5.4.

### Brecha 4 — `status` ignorado
El campo `status` existe en el JSON pero nunca se mapea a ningún estado del Lead en el CRM.
Ver Tarea 5.4.

### Brecha 5 — `owner.phone` no se usa para buscar al Doctor
Hoy el doctor se busca por `unique_id` (= `owner._id`). Si el doctor existe en el CRM pero no tiene `unique_id` asignado (fue creado manualmente), no se matchea aunque tenga el mismo teléfono.
Ver Tarea 5.3.

### Brecha 6 — `eventId` vs `_id` como clave de deduplicación
El JSON tiene dos IDs: `_id` (ID del documento MongoDB) y `eventId` (ID del evento en el calendario SMD). La deduplicación debe usar `_id` del JSON, no el nombre del archivo.

### Brecha 7 — Especialidad siempre `'General'`
El JSON de Dropbox no incluye especialidad explícita, pero `summary` puede contener el nombre del procedimiento (`"Aclaramiento"`, `"Ortodoncia"`, etc.) que podría mapearse a una Specialty.
Pendiente de aclaración con el negocio (ver `00.preguntas-pendientes.md`).
