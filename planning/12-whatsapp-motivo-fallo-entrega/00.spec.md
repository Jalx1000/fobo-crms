# Spec: Motivo de fallo de entrega en WhatsApp (Cloud API)

**Estado:** borrador, pendiente de aprobación
**Fecha:** 2026-10-11
**Origen:** los mensajes a 59167854643 ("Indira", conversación 615) quedan en `failed`
con `error = null`, así que no hay forma de saber por qué.

## Objetivo

Cuando Meta avisa que un mensaje saliente no se pudo entregar, el CRM tiene que
**guardar el motivo** y **mostrarlo en el inbox**. Hoy se descarta.

Meta lo informa de forma asíncrona, en el webhook de estados:

```json
{ "statuses": [{
    "id": "wamid.HBgL...",
    "status": "failed",
    "errors": [{
        "code": 131026,
        "title": "Message undeliverable",
        "message": "Message undeliverable",
        "error_data": { "details": "Message Undeliverable." }
    }]
}]}
```

`CloudApiGateway::parseWebhook()` (línea 133) solo arma `StatusUpdate(id, status)`:
`errors[]` se pierde antes de llegar a `IngestInboundPayload::applyStatus()`.

**Usuario:** la recepcionista que atiende el inbox. Si sabe que el mensaje no llegó
y por qué, puede llamar al paciente o pedirle que actualice WhatsApp.

## Supuestos (corregir antes de aprobar)

1. Solo se cubre el gateway **Cloud API**. Kommo no manda recibos de estado con
   `errors[]` y queda fuera.
2. Se guarda en la columna existente `whatsapp_messages.error`. **Sin migración.**
3. Formato guardado: `"<code> - <title>: <details>"`, por ejemplo
   `131026 - Message undeliverable: Message Undeliverable.`, con `details` solo si
   viene y es distinto del título. Truncado a 500 caracteres, igual que `SendMessage`.
4. El texto queda en inglés, tal como lo manda Meta (el código es lo que sirve para
   buscarlo). Traducir los códigos frecuentes queda como mejora opcional (ver
   Preguntas abiertas).
5. La UI no cambia: `inbox-component.blade.php:194` ya muestra
   `No se envió: {{ msg.error }}` cuando `status === 'failed' && msg.error`.
6. Además de guardarlo, se loguea un `warning` con el código y el `wamid`, **sin el
   teléfono completo** (últimos 4 dígitos, como `searchPatient`).
7. Se respeta la regla actual de "nunca retroceder" del estado. Un `failed` que se
   ignora por llegar tarde tampoco escribe `error`.

## Code Style

Mismo estilo que el módulo: DTOs `final` con constructor promovido, Pint con `=>`
alineado, comentarios que explican el *porqué*.

```php
final class StatusUpdate
{
    public function __construct(
        public string $providerMessageId,
        public string $status,
        public ?string $error = null,   // motivo del proveedor cuando status = failed
    ) {}
}
```

El parámetro es opcional para no romper a otros gateways (Kommo) que construyen
`StatusUpdate` con dos argumentos.

## Testing Strategy

Pest, feature test, `DatabaseTransactions` (**nunca** `RefreshDatabase`: `.env.testing`
apunta a la base de producción).

| Caso | Esperado |
|---|---|
| `parseWebhook` con `failed` + `errors[0]` completo | `StatusUpdate->error = "131026 - Message undeliverable: Message Undeliverable."` |
| `parseWebhook` con `failed` sin `errors` | `error = null`, no explota |
| `parseWebhook` con `delivered` | `error = null` |
| `details` igual al título | no se repite: `"131026 - Message undeliverable"` |
| Ingesta del webhook `failed` sobre un mensaje `sent` | `status = failed`, `error` guardado |
| `failed` que llega después de `read` (mismo rank) | se aplica igual que hoy; documentar el comportamiento en el test |
| `error` de más de 500 caracteres | se trunca |

## Boundaries

- **Siempre:** test primero (debe fallar contra el código actual), Pint, correr
  `--filter Whatsapp` antes de dar por cerrado.
- **Preguntar antes:** migraciones, tocar la UI del inbox, cambiar la regla de
  ranking de estados, reintentos automáticos.
- **Nunca:** loguear el teléfono completo ni el payload entero; usar `RefreshDatabase`;
  commitear sin pedido explícito.

> ⚠️ Este directorio **es producción**: el cambio impacta apenas se guarda el archivo.
> Por eso el orden es: test en rojo → implementación → suite en verde → recién
> entonces queda activo.

## Success Criteria

1. Un webhook real de Meta con `status=failed` deja `whatsapp_messages.error` con
   código y título.
2. En el inbox, el mensaje fallido muestra `No se envió: 131026 - ...` sin tocar la UI.
3. El log tiene un `warning` con `code` y `wamid`, sin el teléfono completo.
4. Los tests nuevos pasan y `--filter Whatsapp` no suma fallos nuevos.
5. **Verificación en producción:** el próximo envío a 59167854643 muestra el motivo
   concreto del fallo.

   también un mapa que hay que mantener. **Propuesta:** no en esta tarea; se puede
   hacer como segunda tarea.
2. Si después de un `failed` llegara un `delivered` (raro, pero Meta no garantiza el
   orden), ¿se limpia `error`? **Propuesta:** no cambiar el ranking actual.
3. ¿Hace falta recuperar el motivo de los 4 mensajes que ya fallaron? No se puede:
   Meta no expone el estado de un mensaje pasado por API. Solo se verá desde el
