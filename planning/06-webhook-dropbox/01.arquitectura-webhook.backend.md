# Tarea 6.1 — Arquitectura: Webhook de Dropbox

**Agente asignado:** `backend`
**Fase:** 06 — Webhook de Dropbox
**Complejidad:** Media-Alta
**Tiempo estimado:** 3h
**Dependencias:** Ninguna (pero coexiste con `smd:sync-dropbox`)

---

## Objetivo

Diseñar el flujo completo desde que Dropbox notifica un cambio hasta que `IncomingAppointmentService` procesa el archivo nuevo, con énfasis en el requisito de respuesta rápida y procesamiento en background.

---

## Flujo completo

```
SMD escribe archivo JSON en Dropbox
        |
        v
Dropbox detecta cambio en la carpeta
        |
        v
POST /api/webhooks/dropbox   (< 2 segundos para responder 200)
        |
   [DropboxWebhookController::handle()]
        |
        ├── Verificar firma HMAC-SHA256
        |       └── Fallo → responder 403, log warning
        |
        └── Válida → responder 200 inmediatamente
                |
                v
        dispatch(new ProcessDropboxNotification())
                |
                v
        [Cola de Laravel — worker procesando en background]
                |
                v
        ProcessDropboxNotification::handle()
                |
                ├── Leer cursor guardado en `od_settings`
                |       └── No hay cursor → inicializar con getInitialCursor()
                |
                ├── Llamar DropboxService::listChanges($cursor)
                |       └── POST files/list_folder/continue con cursor
                |
                ├── Filtrar entries: solo archivos .json nuevos/modificados
                |
                ├── Por cada archivo:
                |       ├── DropboxService::downloadJson($path)
                |       └── IncomingAppointmentService::processDropbox($json)
                |              (misma lógica que smd:sync-dropbox)
                |
                └── Guardar nuevo cursor en `od_settings`
```

---

## Por qué Dropbox requiere respuesta inmediata

Dropbox espera un HTTP 200 en **menos de 10 segundos**. Si el servidor tarda más (o devuelve un error), Dropbox:
1. Reintenta la notificación con backoff exponencial.
2. Después de varios fallos consecutivos, **desactiva el webhook** y notifica al desarrollador por email.

Por eso el controlador **no procesa el archivo directamente** — solo despacha un job y devuelve 200 de inmediato. Todo el trabajo pesado ocurre en el worker de colas.

---

## Persistencia del cursor

### Opción elegida: tabla `od_settings`

El cursor de Dropbox es un string opaco (base64 largo). Se persiste en la tabla `od_settings` existente, que ya se usa para configuración mutable del CRM.

```
Clave: dropbox_cursor
Valor: <cursor string devuelto por Dropbox>
```

Si la tabla `od_settings` no existe aún, se crea como parte de esta fase (ver Tarea 6.4).

### Por qué no Redis

Redis requiere configuración adicional y no está garantizado en el stack actual (Easypanel). La tabla `od_settings` es más robusta y persistente ante reinicios.

### Por qué no `config/smd.php` + `Artisan::call`

Modificar archivos de configuración en disco en runtime es frágil en entornos con OPcache o múltiples workers. La BD es la única fuente de verdad confiable para estado mutable.

---

## Inicialización del cursor

El cursor de Dropbox solo existe si antes hiciste un `files/list_folder` (no `continue`). El flujo de inicialización es:

1. Primera vez (no hay cursor en `od_settings`):
   - `POST files/list_folder` con la carpeta base (`/smd-events`), `recursive: true`
   - Guardar el cursor devuelto (NO procesar los archivos listados — solo capturar el cursor)
   - A partir de ahora, cualquier llamado usa `list_folder/continue`

2. Job recibe notificación y no hay cursor → llama a `getInitialCursor()` automáticamente.

También existe el comando `php artisan smd:dropbox-init-cursor` para inicializar manualmente antes del primer deploy (ver Tarea 6.4).

## Coexistencia con el scheduler

El scheduler `smd:sync-dropbox` puede coexistir sin conflictos porque:
- Usa `smd_synced_events.external_id` como deduplicación
- El job del webhook también pasa por `IncomingAppointmentService::processDropbox()`, que respeta la misma deduplicación
- Si el webhook procesa un archivo y luego el scheduler lo vuelve a ver, el hash md5 del payload no habrá cambiado → `$skipped++`

**Recomendación:** mantener el scheduler con intervalo de 30 minutos como fallback de última instancia.
