# Diseño: citas agendadas para terceros (hijos, familiares)

**Estado:** implementado en el CRM (falta activar en Meta y adaptar el agente) · **Fecha:** 2026-10-12

## Problema

Quien escribe por WhatsApp (o llama) no siempre es el paciente. Un padre agenda para su hijo; días después la madre,
desde otro número, agenda para el mismo hijo. Hoy eso termina en **dos fichas del mismo niño**, porque:

- En el CRM **paciente = quien escribe**: no existe el concepto de "responsable".
- Los familiares solo se relacionan por **compartir teléfono** (`PatientContext::personasDelNumero`), y papá y mamá
  tienen números distintos.
- El teléfono **no identifica a un paciente**: el 50 % de los números de una muestra real tenía 2 o más pacientes en SMD.

**Hoy en los datos:** 5 nombres completos repetidos (10 fichas), ninguno con el patrón papá/mamá, y los 5 también separados
en SMD (probables homónimos). El problema es **a futuro**: aparece cuando el agente empiece a agendar para terceros.

## Idea central

Separar **paciente** (a quién se atiende) de **responsable** (quién escribe, agenda y recibe los avisos). Un paciente
puede tener **varios responsables** (los dos padres), y un responsable, varios pacientes (sus hijos). Al paciente se lo
identifica por **datos de identidad**, nunca por el teléfono de quien agenda.

### Orden de identificación del paciente

| # | Dato | ¿Vincula solo? |
|---|---|---|
| 1 | `smd_patient_id` | Sí (identidad exacta) |
| 2 | Cédula (`ci_paciente`) | Sí |
| 3 | Nombre completo + fecha de nacimiento | Sí, si hay **un solo** candidato |
| 4 | Nombre completo solo, entre los pacientes ya vinculados a este responsable o que comparten su número en SMD | **No**: se propone y se confirma ("¿Es Juan Pérez, nacido el 03/05/2019?") |
| 5 | Nada coincide | Se crea el paciente nuevo y se vincula al responsable |

Nunca se fusiona por nombre solo: dos hermanos o dos homónimos no pueden terminar en la misma ficha.

### Modelo de datos (propuesta)

```
person_relations
  id
  patient_person_id      → persons.id   (el niño)
  responsible_person_id  → persons.id   (papá / mamá / tutor)
  relation               padre | madre | tutor | familiar | otro
  source                 whatsapp | recepcion | smd
  created_at / updated_at
  UNIQUE (patient_person_id, responsible_person_id)
```

- El paciente menor **no hereda el teléfono** del responsable: se lo alcanza a través de sus responsables. Copiar el
  número es justamente lo que hoy vuelve ambiguos los números.
- La cita (lead + actividad) es **del paciente**. El responsable que agendó queda registrado en la cita, para saber a
  quién avisar.

### Flujo (agente IA o recepción)

1. "¿La cita es para vos o para otra persona?"
2. Si es para otra persona: nombre completo, **fecha de nacimiento**, **cédula si tiene** y relación.
3. Buscar con el orden de arriba: primero entre los pacientes ya vinculados a este responsable, después en todo el CRM,
   después en SMD (por cédula o nombre; el número del responsable en SMD suele traer a toda la familia).
4. Encontrado → se vincula este responsable (si es nuevo) y se agenda para ese paciente.
   No encontrado → se crea el paciente, se vincula y se agenda.
5. **Segundo padre, otro día:** el paso 3 encuentra al niño por cédula o por nombre + nacimiento → se suma como segundo
   responsable. **No se crea otra ficha.**

### Lo que esto toca

| Pieza | Cambio |
|---|---|
| BD | Tabla `person_relations` (migración en el paquete Contact) |
| Servicio | `PatientIdentityResolver`: identificación por el orden de arriba; lo usan el agente, la recepción y el sync de SMD |
| API del agente | Endpoint para resolver o crear el paciente tercero (`POST /api/v1/patients/resolve` con datos del paciente + responsable) |
| Agente (crm.py, externo) | Preguntar para quién es la cita y mandar los datos de identidad |
| Recordatorios | Mandarlos al/los responsable(s) cuando el paciente no tiene teléfono propio |
| UI | En la ficha: sección "Responsables" / "A cargo de"; al agendar, elegir paciente entre los vinculados |
| Duplicados existentes | Herramienta de **fusión** de fichas (mueve leads, citas y conversaciones) para los casos que ya existan |

## Decisiones (2026-10-12)

| # | Pregunta | Decisión |
|---|---|---|
| 1 | Dato mínimo de un tercero | **Cédula obligatoria.** Sin CI no se agenda para un tercero (se deriva a recepción). |
| 2 | ¿A quién van los recordatorios? | **A quien agendó** esa cita. |
| 3 | Adultos agendados por otro | **Mismo modelo** de responsable. |
| 4 | ¿Quién captura los datos? | **El agente IA.** |

Consecuencia de (1): el orden de identificación se simplifica. Para un tercero la clave es la **cédula**
(CRM `ci_paciente` → SMD `personID`); nombre + nacimiento solo sirve para confirmar, nunca para vincular solo.

## Cómo consulta el agente al CRM

Ya existe el mecanismo: el CRM le manda al agente un **webhook por cada mensaje** (contacto, historial,
`patient_context`) y el agente responde llamando a la **API REST del CRM con Bearer de Sanctum** (doctores,
disponibilidad, personas, citas, responder, derivar). Los "flows" son **herramientas nuevas** de esa API: el agente
conduce la conversación y el CRM decide la identidad, vincula y agenda.

### Herramientas nuevas

| Herramienta | Endpoint | Hace |
|---|---|---|
| Pacientes a cargo | `GET /api/v1/agent/conversations/{id}/patients` | Lista los pacientes que este responsable ya tiene vinculados (para "¿es para Juan otra vez?"). |
| Resolver paciente tercero | `POST /api/v1/agent/conversations/{id}/patients/resolve` | Recibe `ci`, `name`, `birthdate`, `relation`. Busca en CRM y SMD por **cédula**: `found` (lo vincula a este responsable), `created` (lo crea con datos de SMD si existe allá, y lo vincula) o `mismatch` (la cédula existe con otro nombre → el agente confirma o deriva). |
| Agendar | `POST /api/v1/activities` (ya existe) | Se le agrega `booked_by_person_id` = responsable, para que el recordatorio vaya a quien agendó. |

Además, `patient_context` en el webhook incluirá **los pacientes a cargo** del contacto, así el agente los conoce sin
tener que llamar.

### Conversación tipo (agente)

```
Paciente: Quiero una cita para mi hijo.
Agente:   [lee patient_context → pacientes a cargo: ninguno]
          ¿Me pasás el nombre completo y la cédula de tu hijo?
Paciente: Juan Pérez López, CI 12345678.
Agente:   → POST …/patients/resolve {ci: 12345678, name: "Juan Pérez López", relation: "hijo"}
          ← {status: "found", patient_id: 4521}   (la mamá ya lo había agendado)
          → GET /api/doctors/{id}/available-slots … → POST /api/v1/activities {persons:[4521], booked_by_person_id: 3862}
```

## Decisiones abiertas (resueltas arriba, se conservan por contexto)

1. **Dato mínimo para un menor:** ¿cédula obligatoria, o alcanza con nombre completo + fecha de nacimiento? Muchos niños
   pequeños no tienen cédula.
2. **Recordatorios:** ¿solo al responsable que agendó, o a todos los responsables del paciente?
3. **Adultos agendados por otro** (esposo para esposa, hijo para padre mayor): ¿mismo modelo de "responsable"?
4. **Quién captura los datos:** ¿el agente pregunta todo, o deriva a recepción cuando la cita es para un tercero?
5. **Confirmación del paso 4:** ¿la hace el agente con el responsable, o queda para que recepción la revise?

## Implementación (2026-10-12)

Se resolvió con un **WhatsApp Flow dinámico** ("paciente_tercero"): el agente lo envía, el usuario completa el
formulario dentro del chat y el CRM valida la cédula en vivo desde su endpoint.

| Pieza | Archivo |
|---|---|
| Tabla responsables | `Contact/.../2026_10_12_000001_create_person_relations_table.php` (**ya migrada en producción**) |
| Identidad por cédula + vínculos | `Admin/Services/PatientIdentityResolver.php` |
| Cifrado del endpoint (RSA-OAEP-SHA256 + AES-GCM) | `Whatsapp/Services/Flows/FlowCrypto.php` |
| Token firmado del Flow | `Whatsapp/Services/Flows/FlowToken.php` |
| Pantallas del Flow | `Whatsapp/Services/Flows/PatientFlow.php` + `Whatsapp/Resources/flows/paciente_tercero.json` (Flow JSON 7.3) |
| Endpoint `POST /api/v1/whatsapp/flows/endpoint` | `Whatsapp/Http/Controllers/FlowEndpointController.php` |
| Envío (`interactive` tipo flow) y lectura de `nfm_reply` | `CloudApiGateway` (implementa `SupportsFlows`), `SendMessage` |
| Herramienta del agente `POST …/conversations/{id}/flows` | `AgentController::sendFlow` |
| `pacientes_a_cargo` y sus citas en el webhook | `PatientContext` |
| Comandos | `whatsapp:flows:keys`, `whatsapp:flows:publish` |
| Contrato para el agente | `docs/agente-ia-integracion.md` §7 |
