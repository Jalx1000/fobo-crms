# Tarea 8.7 — Confirmar y optimizar `GET /api/doctors/{id}`

**Agente asignado:** `backend`
**Fase:** 08 — Agente WhatsApp
**Complejidad:** Baja
**Tiempo estimado:** 1h
**Dependencias:** Ninguna

---

## Objetivo

El endpoint `GET /api/doctors/{id}` ya existe pero necesita verificación y posible optimización: el agente de WhatsApp actualmente carga los ~100 doctores con `GET /api/doctors` y filtra en Python, cuando podría consultar por ID directamente. Esta tarea confirma que el endpoint existente es suficiente para el agente y documenta cualquier mejora necesaria.

## Contexto

**Estado actual (ya investigado):**

El endpoint `GET /api/doctors/{id}` ya está implementado en:
- Ruta: `packages/Webkul/Doctor/src/Routes/api.php` línea 4 — `Route::get('doctors/{id}', [DoctorController::class, 'show'])->name('api.doctors.show')`
- Controlador: `packages/Webkul/Doctor/src/Http/Controllers/Api/DoctorController::show($id)`
- Middleware: `api` (sin Sanctum) — **accesible sin token**

**Lo que devuelve `show($id)` actualmente:**
```json
{
  "id": 1,
  "name": "Dr. García",
  "specialties": [...],
  "attribute_values": [...],
  "schedule": [
    { "date": "2026-05-24", "slots": [{"start_time": "09:00", "end_time": "10:00", "status": "available"}] },
    ...
  ]
}
```

Devuelve doctor + schedule de los próximos 6 días usando `DoctorAvailabilityService::weekScheduleForDoctor()`.

**Problema identificado:** El agente usa `GET /api/doctors` (lista paginada, devuelve todos con paginación de 10-100) y filtra localmente en Python. Con ~100 doctores esto es:
- ~1-10 requests para cargar todos los doctores
- Procesamiento Python para filtrar por ID
- Sin datos de `end_time` en el endpoint de lista

La solución ya existe: `GET /api/doctors/{id}` devuelve un solo doctor con su schedule.

**Nota de autenticación:** La ruta está bajo middleware `api` (sin Sanctum), igual que `GET /api/doctors`. Esto es consistente con el diseño actual del módulo Doctor, que expone datos públicos de disponibilidad para el agente sin requerir token. Si se necesita proteger, ver la sección de opciones.

### Paso 5 — Documentar para el equipo del agente WhatsApp

El agente debe reemplazar su flujo actual:

**Flujo actual (ineficiente):**
```python
# Python del agente (actual)
doctors = requests.get(f"{CRM_URL}/api/doctors?limit=100").json()
```

**Flujo recomendado:**
```python
# Python del agente (optimizado)
response = requests.get(
    f"{CRM_URL}/api/doctors/{doctor_id}",
    headers={"Accept": "application/json"}
)
doctor = response.json()
# doctor['schedule'] ya contiene disponibilidad de los próximos 6 días
# doctor['schedule'][0]['slots'] contiene start_time y end_time
```

### Paso 6 — (Opcional) Añadir Sanctum al endpoint de doctor si el PO lo requiere

Si el PO decide proteger el endpoint de doctors con el mismo token del agente:

```php
// En packages/Webkul/Doctor/src/Routes/api.php
// Cambiar de:
Route::prefix('api')->group(function () {
    Route::get('doctors/{id}', [DoctorController::class, 'show'])->name('api.doctors.show');
});

// A:
Route::prefix('api')->middleware('auth:sanctum')->group(function () {
    Route::get('doctors/{id}', [DoctorController::class, 'show'])->name('api.doctors.show');
});
```

**Advertencia:** Cambiar el middleware rompería cualquier llamada sin token. Evaluar impacto antes de aplicar.

## Criterios de aceptación

- [ ] `GET /api/doctors/{id}` con un ID válido devuelve `200` con el doctor y su schedule
- [ ] `GET /api/doctors/{id}` con ID inexistente devuelve `404` con `{"message": "Doctor not found"}`
- [ ] `GET /api/doctors/{id}` con ID no numérico devuelve `400` con `{"message": "Invalid doctor ID format"}`
- [ ] Los slots en `schedule` incluyen `end_time` (no solo `start_time`)
- [ ] El tiempo de respuesta es inferior al de `GET /api/doctors?limit=100` (reducción de payload)
- [ ] El equipo del agente WhatsApp recibe la documentación del endpoint (URL, estructura de respuesta, sin necesidad de token)
