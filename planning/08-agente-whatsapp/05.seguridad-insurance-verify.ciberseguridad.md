# Tarea 8.5 — Rate limiting + Audit log + Anti-enumeración para `/api/v1/insurance/verify`

**Agente asignado:** `ciberseguridad`
**Fase:** 08 — Agente WhatsApp
**Complejidad:** Media
**Tiempo estimado:** 2h
**Dependencias:** Tarea 8.4

---

## Objetivo

Añadir los tres requerimientos de seguridad obligatorios al endpoint `GET /api/v1/insurance/verify`:

1. **Rate limiting:** máx 10 requests/min por token
2. **Audit log:** registrar `{ token_hash, ci_hash, seguro_hash, timestamp, result: bool }` — nunca valores en claro
3. **Revisar anti-enumeración:** confirmar que la respuesta no permite distinguir "paciente no encontrado" de "paciente sin seguro"

## Contexto

El endpoint creado en Tarea 8.4 ya tiene Sanctum. Pero un token comprometido podría usarse para:
- **Brute-force de CIs** — probar millones de cédulas para detectar qué pacientes están en el sistema
- **Reconocimiento de aseguradoras** — saber qué empresas tienen cobertura con qué CIs
- **Exposición de datos personales** — nombre, `patient_id`, póliza

Los requerimientos de seguridad son obligatorios porque `ci_paciente` es un dato de identificación personal (boliviano: CI = cédula de identidad).

**Estado actual del throttle:**

El `AdminServiceProvider` carga el archivo `insurance.php` bajo `throttle:api`. El throttle `api` de Laravel por defecto es `60 req/min` (configurable en `RouteServiceProvider`). Necesitamos un throttle más estricto de `10 req/min` específico para este endpoint.

## Implementación

### 1. Named Rate Limiter: `insurance-agent` (10 req/min por token)

Archivo: `app/Providers/RouteServiceProvider.php`

En el método `configureRateLimiting()`, añadir:

```php
use Illuminate\Support\Facades\RateLimiter;
use Illuminate\Http\Request;

protected function configureRateLimiting(): void
{
    // ... throttles existentes ...

    // Rate limiter específico para verificación de seguros desde el agente
    RateLimiter::for('insurance-agent', function (Request $request) {
        // Limitar por token (tokenable_id + token_hash) para que cada token tenga su cuota
        $tokenId = optional($request->user()?->currentAccessToken())->id ?? 'unauthenticated';

        return \Illuminate\Cache\RateLimiting\Limit::perMinute(10)
            ->by('insurance-agent|' . $tokenId)
            ->response(function () {
                return response()->json([
                    'message' => 'Too many requests. Maximum 10 verifications per minute per token.',
                    'retry_after' => 60,
                ], 429);
            });
    });
}
```

Registrar el throttle en la ruta:

### 3. Llamar al audit log desde el controlador

Archivo: `packages/Webkul/Admin/src/Http/Controllers/Api/InsuranceController.php`

Añadir al final del método `verifyForAgent()`, antes de cada `return response()->json(...)`:

```php
// ── Audit log (siempre, independientemente del resultado) ─────────────────
$this->logAudit(
    request: $request,
    ci:      $ci,
    seguro:  $seguroName,
    result:  $hasInsurance,
);
```

Añadir el método privado `logAudit()` a la clase:

```php
private function logAudit(Request $request, string $ci, string $seguro, bool $result): void
{
    try {
        $tokenId = optional($request->user()?->currentAccessToken())->token ?? 'unknown';

        \Illuminate\Support\Facades\DB::table('insurance_audit_logs')->insert([
            'token_hash'  => hash('sha256', $tokenId),
            'ci_hash'     => hash('sha256', $ci),
            'seguro_hash' => hash('sha256', strtolower(trim($seguro))),
            'result'      => $result,
            'ip_address'  => $request->ip(),
            'created_at'  => now(),
        ]);
    } catch (\Throwable $e) {
        // El audit log NUNCA debe romper el flujo principal.
        // Loguear el error pero no propagar la excepción.
        \Illuminate\Support\Facades\Log::error('[InsuranceAudit] Error al escribir audit log', [
            'error' => $e->getMessage(),
        ]);
    }
}
```

**Nota de seguridad crítica:** `$request->user()->currentAccessToken()->token` devuelve el hash SHA-256 del token que ya almacena Sanctum internamente (no el token en claro). Hacer `hash('sha256', ...)` sobre ese hash es doble-hash, lo cual es correcto — evita que el audit log pueda usarse para recuperar el token original.

### 4. Revisión anti-enumeración

Verificar que el método `verifyForAgent()` devuelve exactamente la misma respuesta para:

| Escenario | Respuesta correcta | Respuesta incorrecta (fuga) |
|-----------|-------------------|----------------------------|
| CI no existe en la BD | `{"has_insurance":false,"patient_found":false}` | `{"has_insurance":false,"patient_found":false,"error":"CI no encontrado"}` |
| CI existe pero no tiene seguro | `{"has_insurance":false,"patient_found":false}` | `{"has_insurance":false,"patient_found":true}` ← FUGA |
| CI existe y seguro vencido | `{"has_insurance":false,"patient_found":false}` | `{"has_insurance":false,"status":"VENCIDO"}` ← FUGA |
| CI existe y seguro activo | `{"has_insurance":true,...}` | — |

La columna `patient_found` siempre debe ser `false` cuando `has_insurance` es `false`. No se distingue entre "no encontrado" y "encontrado pero sin seguro".

**Revisar el tiempo de respuesta:** Si el lookup EAV tarda más cuando el paciente existe (vs. cuando no existe), hay un timing oracle. Para mitigarlo:

```php
// En verifyForAgent(), añadir un sleep mínimo de 50ms para uniformizar
// Solo en caso de has_insurance: false para evitar distinguir por tiempo
if (! $hasInsurance) {
    // Uniformizar tiempo de respuesta (anti-timing oracle)
    usleep(random_int(50000, 150000)); // 50-150ms
    return response()->json(['has_insurance' => false, 'patient_found' => false]);
}
```
