## Objetivo

Auditar y fortalecer el endpoint `POST /api/webhooks/sharemedata` que recibe citas desde ShareMeData. Identificar vulnerabilidades y producir un PR con fixes.

## Archivo a auditar

```
packages/Webkul/Admin/src/Http/Controllers/ShareMeDataWebhookController.php
routes/api.php  (línea donde se registra la ruta)
```

## Checklist de auditoría

### 1. Autenticación del webhook

```php
// Verificar en ShareMeDataWebhookController::receive()
$secret = config('services.sharemedata.webhook_secret');
if ($secret) {
    $token = $request->header('X-Webhook-Secret') ?? $request->query('secret');
    if ($token !== $secret) {
        return response()->json(['message' => 'Unauthorized'], 401);
    }
}
```

**Puntos a verificar:**
- [ ] ¿Qué pasa si `SHAREMEDATA_WEBHOOK_SECRET` está vacío en `.env`? Actualmente acepta TODO sin autenticación.
- [ ] ¿El secret está loggeado en algún log de acceso de Nginx o Laravel?
- [ ] ¿La comparación usa `hash_equals()` para prevenir timing attacks?

**Fix recomendado:**

```php
// Usar comparación segura
if (! hash_equals((string) $secret, (string) $token)) {
    return response()->json(['message' => 'Unauthorized'], 401);
}
```

### 2. Schema del payload vs. API v2 (Dropbox)

El webhook actual espera:
```json
{ "physician": { "_id": "..." }, "patient": { "phone": "..." }, "slot": {...} }
```

El schema del PDF v2 (Dropbox) usa:
```json
{ "attendances": [...], "owner": {...}, "startDate": "...", "endDate": "..." }
```

**Riesgo:** Si SMD actualiza su Webhook al nuevo formato, el controlador deja de funcionar sin warning.

- [ ] Confirmar con SMD si el formato del Webhook cambiará en v2
- [ ] Documentar la divergencia en código con comentario explícito

### 3. Rate limiting

- [ ] ¿El endpoint tiene rate limiting? Si SMD envía muchos eventos seguidos, ¿puede saturar el sistema?
- [ ] Verificar en `routes/api.php` si hay middleware `throttle` aplicado
- [ ] Recomendación: `throttle:60,1` (60 requests por minuto)

### 4. Validación del payload

```php
// Validación actual
if (!isset($data['physician']['_id']) || !isset($data['patient']['phone'])) {
    return response()->json(['message' => 'Datos incompletos'], 400);
}
```

- [ ] ¿Se valida que `slot.start` y `slot.end` sean fechas válidas?
- [ ] ¿Se valida que `physician._id` no sea una cadena de inyección?
- [ ] Agregar validación con `$request->validate([...])` en lugar de `isset` manual

### 5. Exposición de información en errores

- [ ] El catch devuelve `['message' => 'Error interno']` — ✅ correcto, no expone stack trace
- [ ] Verificar que `APP_DEBUG=false` en producción (ya está, confirmar)

## Entregables

2. **PR** — Fixes de los hallazgos críticos y altos

- [ ] La comparación del secret usa `hash_equals()`
- [ ] Si `SHAREMEDATA_WEBHOOK_SECRET` está vacío, el sistema loguea un warning al arrancar (o el webhook requiere el secret siempre en producción)
- [ ] Rate limiting aplicado al endpoint
- [ ] Validación del payload usa Form Request o `$request->validate()`
