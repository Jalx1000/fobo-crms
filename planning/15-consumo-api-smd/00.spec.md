# Spec: Consumo de la API de ShareMeData dentro del presupuesto

**Estado:** borrador para revisión · **Fecha:** 2026-10-13 · **Origen:** correo de shareMEData (Christian Velasco) cortando el acceso a la API

## Contexto e incidente

shareMEData cortó el acceso de Sofopolis a su API: "más de 5.700 requests en 17 horas, aproximadamente cada 5 segundos". OdontoKing contrató **10.000 requests/mes** (120.000/año). El excedente cuesta Bs 5.880 cada 15 días.

### Causa raíz (medida, 2026-10-13)

El **catálogo de horarios del formulario de WhatsApp** (`whatsapp:booking-catalog`, agregado el 2026-10-12):

- Corría cada 10 minutos y armaba la disponibilidad de **59 pares doctor-especialidad** (17 doctores) para 50 días.
- Hacía una llamada `GET /schedule/availability` por par.
- **97 armados × 59 = ~5.723 requests** entre 07:40 y ~00:40 (17 h): una cada ~7 s.
- Se sumaba el refresco tras cada cancelación o reprogramación (`RefreshBookingSlots`), del orden de 100 requests.

Se diseñó así para que el formulario respondiera dentro de los ~10 s que da Meta, sin calcular el costo contra la cuota.

### Consumo de base sin el catálogo (estimado desde datos; no hay registro de cada request)

| Fuente | Volumen observado | Requests a SMD estimados |
|---|---|---|
| Sync Dropbox: ficha de paciente nuevo (`SmdPatientDirectory`, caché 7 días) | 20–40 pacientes nuevos/día (hasta ~200 eventos) | 30–200/día |
| Citas creadas desde el CRM / formulario (validar, paciente, crear evento, PATCH) | 1–7/día | 10–40/día |
| Listeners de personas (`updateInSmd`), `search-smd`, `smd-data`, `link-smd` | ~15/día | ~15/día |
| API de disponibilidad del agente | 4 en 3,5 días | ~1/día |
| **Total de base** | | **~60–250/día ≈ 2.000–7.500/mes** |

**Mitigación ya aplicada (2026-10-13, antes de esta spec):** el catálogo y su refresco quedaron apagados con `WHATSAPP_BOOKING_CATALOG=false`. Mientras siga así, el formulario de agendar no ofrece horarios y deriva a recepción. Revertir o dejarlo es una decisión pendiente (ver Preguntas abiertas).

## Decisiones (2026-10-13)

- **Tope de 800 consultas por día.**
- **Horarios del formulario solo al elegir la especialidad:** 1 consulta a SMD por la especialidad elegida, que devuelve todos sus doctores, esperando la respuesta.
- Plan detallado: [01.plan.md](01.plan.md).

## Supuestos (corregir antes de seguir)

1. La cuota cuenta **toda** llamada a la API de SMD, incluidas las que fallan. Los webhooks que SMD nos manda, y Dropbox, **no** cuentan.
2. El objetivo es quedar **por debajo de ~50 % de la cuota en un día normal** (≤ 150 requests/día, ~4.500/mes), con margen para picos.
3. La agenda local del CRM refleja SMD casi en tiempo real: cada cambio de SMD llega por el webhook de Dropbox en segundos, incluidos bloqueos y cancelaciones. Por eso alcanza para **ofrecer** horarios en el formulario, siempre que la reserva se valide en vivo contra SMD con 1 request.
4. `doctor_shifts` (jornada local) está cargada y al día para los doctores reservables.
5. No se agregan dependencias nuevas ni tablas grandes; un contador diario en caché (Redis) es suficiente.

## Objetivo

Que la integración con SMD consuma una cantidad **predecible, medida y acotada** de requests, demostrable ante shareMEData y OdontoKing, sin perder las funciones de agenda.

Criterios de éxito:

- **CE-1:** Cada request a la API de SMD queda registrada con endpoint, origen (qué función la disparó) y resultado. Hay un conteo diario y mensual consultable con un comando.
- **CE-2:** El formulario consulta la disponibilidad de SMD **solo al elegir la especialidad**: 1 request por especialidad, guardada 5 min. Más 1 al confirmar y las de crear el evento.
- **CE-3:** Ningún proceso programado consulta SMD en bucle. Ningún job recorre doctores o especialidades contra la API.
- **CE-4:** Hay un **tope diario configurable (800)**. Al alcanzarlo se cortan las llamadas no esenciales (búsquedas, refrescos, diagnósticos) y se conservan las esenciales (crear o actualizar citas). Se loguea y se avisa.
- **CE-5:** En un día normal el consumo medido es ≤ 150 requests, verificado con el contador durante 7 días antes de pedir la reactivación.
- **CE-6:** Hay un informe para shareMEData y OdontoKing con la causa, la corrección y el consumo medido.

## Alcance

**Incluye:**
- Registro y contador de todas las llamadas en `ShareMeDataService`, que es el único punto de salida HTTP a SMD.
- Disponibilidad local para el formulario.
- Validación en vivo única al reservar y al reprogramar.
- Tope diario con prioridad esencial / no esencial.
- Revisión del costo de cada camino que llama a SMD.
- Comando de reporte e informe.

**No incluye:** cambiar la sincronización por Dropbox, ni negociar el contrato.

## Estilo de código

Igual al resto del paquete: servicios inyectados, comentarios en español que explican el porqué, Pint con `=>` alineados. Ejemplo de la forma esperada para el punto de salida:

```php
protected function http(string $source, bool $essential = false): PendingRequest
{
    // Cada request cuenta contra la cuota contratada (10.000/mes): se registra
    // y, pasado el tope diario, solo pasan las esenciales (crear/editar citas).
    $this->budget->spend($source, $essential);

    return Http::withHeaders([...])->timeout(...);
}
```

## Estrategia de tests

Pest, con `Http::fake` y el router de `tests/Support/SmdAuditHelpers.php`:

- Contador: cada método de `ShareMeDataService` suma 1 con su origen. Una falla también cuenta.
- Tope: pasado `daily_cap`, una llamada no esencial lanza o devuelve "sin cuota" **sin hacer HTTP**, y una esencial pasa y se loguea.
- Formulario: recorrer agendar completo **sin ninguna request a `/schedule/availability`** hasta confirmar; al confirmar, exactamente 1.
- Catálogo: armarlo no hace HTTP (`Http::assertNothingSent` para SMD).
- Regresión de presupuesto: un test que simula un día típico (N eventos Dropbox, M citas, K contactos) y verifica que el total ≤ 150.

## Límites

- **Siempre:** medir antes y después; toda llamada nueva a SMD pasa por `ShareMeDataService` y declara su origen; tests en cada cambio.
- **Preguntar primero:** reactivar cualquier proceso que consulte SMD; cambiar el tope; tocar producción (`.env`, procesos, workers); escribirle a shareMEData.
- **Nunca:** jobs programados que recorran doctores o especialidades contra la API; reintentos automáticos en bucle contra SMD; llamar a SMD desde fuera de `ShareMeDataService`.

## Preguntas abiertas

1. **Catálogo apagado hoy:** ¿lo dejamos apagado hasta tener la versión local (el formulario deriva a recepción), o se revierte? Igual no tiene acceso a la API mientras SMD no la reactive.
2. **Objetivo diario:** ¿≤ 150/día está bien, o OdontoKing quiere otro número? ¿Quién confirma con shareMEData qué cuenta como request (¿las fallidas?)?
3. **Tope duro:** al llegar al tope, ¿se bloquean también las citas creadas desde el CRM, o esas siempre pasan?
4. **Confianza en la agenda local:** ¿hay casos donde SMD bloquea horarios que no llegan por Dropbox (ej. feriados cargados solo en SMD)? Si los hay, la validación en vivo al confirmar los atrapa, pero el paciente vería un horario que después se rechaza.
5. **Detalle de SMD:** ¿pedimos a shareMEData el desglose por endpoint de esas 5.700 requests, para contrastarlo con este análisis?
