# Auditoría - Citas canceladas bloquean el slot para nuevas citas

Fecha: 2026-06-17
Scope: Creación de citas desde el Admin (`AppointmentService`), sincronización de cancelaciones desde SMD (`IncomingAppointmentService`).

---

## Hallazgo principal

Cuando una cita se cancela **en SMD** (vía Dropbox, `archived: true` o `status: "CANCELED"`), el flujo actual:

1. `IncomingAppointmentService::cancelDropbox()` cierra el **Lead** (`status = 0`, `lead_pipeline_stage_id` = cancelado, tag "Cancelado").
2. La **Activity** asociada **no se toca** - sigue existiendo con el mismo `schedule_from` / `schedule_to`, vinculada al doctor vía `doctor_activities`.

Cuando alguien intenta crear una **nueva** cita en ese mismo horario desde el Admin, `AppointmentService::process()` (`packages/Webkul/Admin/src/Services/AppointmentService.php:96-118`) hace esta validación:

```php
// ── 2. Validar conflicto local ────────────────────────────────────────
$localConflict = DB::table('activities')
    ->join('doctor_activities', 'activities.id', '=', 'doctor_activities.activity_id')
    ->where('doctor_activities.doctor_id', $doctorId)
    ->where(function ($query) use ($scheduleFrom, $scheduleTo) { /* overlap */ })
    ->exists();

if ($localConflict) {
    throw new AppointmentException("El doctor ya tiene una cita programada en este horario en el sistema local.");
}
```

**Esta consulta no filtra por el estado del Lead asociado a la Activity.** Por lo tanto, una Activity cuyo Lead ya está cerrado/cancelado sigue contando como "ocupado", y el sistema rechaza la creación de una cita nueva en ese horario - aunque SMD ya liberó el slot.

## Por qué no se nota siempre

- Si el doctor tiene pocos turnos o el horario cancelado no se reintenta, el bug pasa inadvertido.
- El paso 4 (verificación SMD, líneas 172-251) sí confirmaría que el slot está libre en SMD - pero nunca se llega a ese paso porque el conflicto local corta el flujo antes (línea 114-118).

## Relación Activity ↔ Lead

`Activity` tiene relación `belongsToMany` hacia `Lead` vía la tabla pivote `lead_activities` (`packages/Webkul/Activity/src/Models/Activity.php:84-87`). Esto permite hacer el join necesario para excluir Leads cerrados.

`leads.status` es boolean: `1`/`null` = abierto, `0` = cerrado (estándar Krayin). Al cancelar desde SMD se setea `status = 0` y `lost_reason`.

## Regla de negocio a implementar

> Una Activity cuyo Lead está cerrado (`status = 0`) **no debe contar como conflicto local**. El sistema debe permitir intentar crear una cita nueva en ese horario - pero **siempre validando disponibilidad real en SMD** (paso 4, ya existente) antes de confirmar la creación.

Es decir: el chequeo local de conflicto pasa a ser "¿hay una cita *activa* (Lead abierto) en este horario?" en vez de "¿existe alguna Activity en este horario, sin importar su estado?". La verificación de SMD (que ya existe y es la fuente de verdad) sigue siendo obligatoria y no se modifica - solo deja de estar bloqueada artificialmente por una Activity huérfana de un Lead cancelado.

---

## Qué NO cambia

- El flujo de verificación de disponibilidad en SMD (`ShareMeDataService::checkAvailability()`, paso 4) permanece intacto - sigue siendo el gate definitivo antes de crear el evento.
- El flujo de cancelación desde SMD (`cancelDropbox()`) no se modifica - sigue sin borrar la Activity, solo cierra el Lead.
- La validación de turno/jornada (paso 1, `doctor_shifts`) no se modifica.

## Qué cambia

- La query de conflicto local (paso 2) excluye Activities cuyo Lead vinculado está cerrado (`status = 0`).
- Activities **sin** Lead vinculado (huérfanas, si las hay) se mantienen como conflicto por seguridad - no se asume que están libres.

## Riesgo identificado a confirmar con el usuario

Si dos Leads abiertos distintos llegan a compartir Activities solapadas por algún bug previo de sincronización, este cambio no los afecta (siguen bloqueando, porque ambos Leads están abiertos). El cambio solo libera el slot cuando **todas** las Activities solapadas pertenecen a Leads cerrados.

## Confirmado con el usuario (2026-06-17)

- **Origen de la cancelación:** manual en el CRM - un agente abre el Lead en el Admin y lo marca como perdido/cancelado directamente en el pipeline (no necesariamente vía SMD/Dropbox).
  - Esto **no cambia el fix**: la cancelación manual también deja `leads.status = 0` (mecanismo estándar de Krayin), exactamente la misma condición que ya cubre la Tarea 9.1. No se requiere lógica adicional para distinguir "cancelado en SMD" vs "cancelado manualmente".
- **Punto de entrada de la cita nueva:** confirmado que existe un único punto de entrada para crear citas - `AppointmentService::process()`, invocado tanto desde el modal "Añadir cita" del Admin (`ActivityController::storeAppointment()`) como desde `POST /api/v1/activities` (`App\Http\Controllers\Api\V1\ActivityController::store()`, el endpoint que usaría el agente de WhatsApp). No hay un segundo flujo de creación que evite o duplique la validación de conflicto local - el fix de la Tarea 9.1 cubre ambas superficies sin cambios adicionales.

## Hallazgo adicional al verificar contra producción (2026-06-17)

Al reproducir el caso real reportado por el usuario (doctor_id=21, 2026-06-17 11:00-12:00) consultando directamente la BD de producción (vía `docker exec` al contenedor `heaven_odontoking-crm`, solo lectura), se encontró que el supuesto de la Tarea 9.1 era incompleto:

**La cancelación manual en este CRM no necesariamente toca `leads.status`.** El Lead 907 (vinculado a la Activity 17728 que bloqueaba el slot) tenía:
- `status` = `NULL` (no `0`)
- `lost_reason` = vacío
- `closed_at` = vacío
- `lead_pipeline_stage_id` = `6` (stage "Cancelado", que coincide exactamente con `config('smd.stage_map.cancelled')`)

Es decir: alguien movió el Lead al stage "Cancelado" desde el pipeline del Admin (drag & drop o equivalente), pero esa acción **no** dispara el mecanismo estándar de Krayin de "lost" (`status=0` + `lost_reason` + `closed_at`). Solo `cancelDropbox()` (cancelación vía SMD) seteaba status=0 explícitamente.

**Corrección aplicada a la Tarea 9.1:** el chequeo de conflicto local ahora considera "cancelado" si **cualquiera** de estas dos condiciones se cumple:
1. `leads.status = 0` (mecanismo estándar Krayin, vía `cancelDropbox()`)
2. `leads.lead_pipeline_stage_id` está en `[config('smd.stage_map.cancelled'), config('smd.stage_map.no_show')]`

**Bug de SQL detectado y corregido en el camino:** `NULL NOT IN (...)` en SQL evalúa a `NULL` (no a `true`), así que un Lead recién creado con `lead_pipeline_stage_id = NULL` (default de `Lead::create()`) rompía silenciosamente la exclusión. Se agregó `whereNull('leads.lead_pipeline_stage_id')` explícito junto al `whereNotIn` para que un stage NULL siga contando como "abierto/bloqueante" (comportamiento conservador).

Verificado contra producción (solo lectura): con el fix corregido, el query devuelve `false` (sin conflicto) para el caso real del doctor 21. Test de regresión agregado: `it('libera el slot cuando el lead se cancelo solo moviendo el stage, sin tocar status')` en `tests/Feature/AppointmentConflictAfterCancellationTest.php`.
