# Tarea 9.1 - Excluir Leads cerrados del chequeo de conflicto local

**Agente asignado:** `backend`
**Fase:** 09 - Disponibilidad tras cancelación
**Complejidad:** Baja
**Tiempo estimado:** 1-2h
**Dependencias:** Ninguna (no requiere migraciones)

---

## Objetivo

Que una cita cancelada en SMD (Lead cerrado, `status = 0`) deje de bloquear la creación de una cita nueva en el mismo horario/doctor, sin debilitar la verificación de disponibilidad en SMD que ya existe y debe seguir siendo obligatoria.

---

## Archivo a modificar

`packages/Webkul/Admin/src/Services/AppointmentService.php` - método `process()`, bloque `── 2. Validar conflicto local ──` (líneas ~96-118).

---

## Cambio propuesto

Unir también con `lead_activities` + `leads` y excluir activities cuyo(s) Lead(s) asociados estén **todos** cerrados (`status = 0`). Si la Activity no tiene Lead vinculado, se sigue tratando como conflicto (comportamiento conservador).

```php
// ── 2. Validar conflicto local ────────────────────────────────────────
// Excluye activities cuyo Lead está cerrado (cancelado/perdido en SMD):
// una cita cancelada no debe bloquear el slot para una cita nueva.
$localConflict = DB::table('activities')
    ->join('doctor_activities', 'activities.id', '=', 'doctor_activities.activity_id')
    ->where('doctor_activities.doctor_id', $doctorId)
    ->where(function ($query) use ($scheduleFrom, $scheduleTo) {
        $query->where(function ($q) use ($scheduleFrom, $scheduleTo) {
            $q->where('schedule_from', '>=', $scheduleFrom)
              ->where('schedule_from', '<', $scheduleTo);
        })->orWhere(function ($q) use ($scheduleFrom, $scheduleTo) {
            $q->where('schedule_to', '>', $scheduleFrom)
              ->where('schedule_to', '<=', $scheduleTo);
        })->orWhere(function ($q) use ($scheduleFrom, $scheduleTo) {
            $q->where('schedule_from', '<=', $scheduleFrom)
              ->where('schedule_to', '>=', $scheduleTo);
        });
    })
    ->where(function ($query) {
        $query->whereNotExists(function ($sub) {
            // Activity con al menos un lead vinculado...
            $sub->select('id')
                ->from('lead_activities')
                ->whereColumn('lead_activities.activity_id', 'activities.id');
        })->orWhereExists(function ($sub) {
            // ...y al menos uno de esos leads sigue abierto (status != 0)
            $sub->select('id')
                ->from('lead_activities')
                ->join('leads', 'leads.id', '=', 'lead_activities.lead_id')
                ->whereColumn('lead_activities.activity_id', 'activities.id')
                ->where(function ($q) {
                    $q->whereNull('leads.status')->orWhere('leads.status', '!=', 0);
                });
        });
    })
    ->exists();

if ($localConflict) {
    throw new AppointmentException(
        "El doctor ya tiene una cita programada en este horario en el sistema local."
    );
}
```

### Por qué `whereNotExists OR whereExists` y no un simple `leftJoin`

- Una Activity puede tener **0 o varios** Leads (relación `belongsToMany` vía `lead_activities`).
- Si tiene 0 Leads → se sigue considerando conflicto (no asumimos que está libre solo porque no hay vínculo, evita falsos negativos por datos inconsistentes).
- Si tiene 1+ Leads → solo deja de ser conflicto si **todos** están cerrados. Por eso se usa `whereExists` con "al menos un lead abierto" para que SIGA contando como conflicto si hay algún lead abierto, y la ausencia de ese `whereExists` (combinada con que sí haya leads) implica que todos están cerrados.

Repasar con cuidado la lógica booleana al implementar - preferible cubrir con tests explícitos (Tarea 9.2) en vez de razonar solo en abstracto.

## Criterios de aceptación

- [ ] Una Activity vinculada a un Lead con `status = 0` (cerrado/cancelado) en el horario solicitado **no** genera `AppointmentException` por conflicto local.
- [ ] Una Activity vinculada a un Lead con `status = 1` o `null` (abierto) en el horario solicitado **sigue** generando `AppointmentException` por conflicto local (sin regresión).
- [ ] Una Activity **sin** Lead vinculado en el horario solicitado **sigue** generando conflicto (comportamiento conservador, sin cambios).
- [ ] Si la Activity tiene múltiples Leads y al menos uno está abierto, sigue contando como conflicto.
- [ ] El paso 4 (verificación SMD) sigue ejecutándose y sigue pudiendo rechazar la creación aunque el paso 2 ya no bloquee - es decir, "libre localmente" no implica "libre en SMD".
- [ ] Tests existentes de `ActivityConflictTest.php` siguen pasando sin modificación (ese test cubre `ActivityRepository::isDurationOverlapping`, no este método - confirmar que no se solapan ambas validaciones de forma contradictoria).
