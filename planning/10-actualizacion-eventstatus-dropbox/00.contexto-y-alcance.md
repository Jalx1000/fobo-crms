## TL;DR (leer esto si no lees nada más)

1. SMD ya desplegó su cambio: ahora **cada modificación de una cita genera un archivo nuevo** en la carpeta Dropbox del día en curso, con un atributo nuevo `eventStatus: CREATED | UPDATED`.
2. **El `eventStatus` no nos hace falta.** El CRM ya distingue "crear" de "modificar" por el `_id`, que se mantiene igual entre archivos. Es un dato de confirmación, no la solución.
3. **El problema real es otro:** los archivos viejos **no se borran**. El sync recorre las carpetas de la más nueva a la más vieja, y como "el último archivo procesado gana", **el archivo viejo pisa al nuevo y revierte la modificación**.
4. Consecuencia hoy, con datos reales: la cita `6a54f35…` está el **17 de julio** en SMD y el CRM la va a mostrar el **21 de julio**.
5. El arreglo es acotado: **ordenar por `updated_at` y no aplicar payloads viejos**. No depende de ninguna respuesta de SMD.
6. Hay **2 bugs preexistentes en `DropboxService`** que pueden tumbar el sync entero y que conviene arreglar en el mismo lote.
7. Queda **1 pregunta abierta para Mauri**: dónde viene el médico. En los 4 archivos actuales no está.

## Parte 1 - Cómo funciona el sync hoy (contexto necesario)

Sin esto, el resto no se entiende. Hay **dos caminos** que hacen lo mismo por vías distintas:

### Camino A - El cron (el que importa para este análisis)

```
app/Console/Kernel.php
  └─ cada 5 min: smd:sync-dropbox --days=2   (si el sync no está pausado)
       └─ SmdAppointmentSyncService::run()
            └─ para cada día (hoy, hoy-1):
                 DropboxService::listFilesForDate()  → lista archivos JSON de esa carpeta
                 DropboxService::downloadJson()      → baja cada archivo
                 IncomingAppointmentService          → crea/actualiza/cancela Lead + Activity
```

### Camino B - El webhook

```
POST /api/webhooks/dropbox  (Dropbox avisa que algo cambió)
  └─ DropboxWebhookController::handle()  → valida firma HMAC
       └─ ProcessDropboxNotification (job)
            └─ DropboxService::listChanges($cursor)  → cambios desde el último cursor
```

### Cómo decide crear vs. actualizar

Tabla `smd_synced_events`, con `external_id` (= el `_id` del JSON) **único**:

| Situación | Qué hace |
|---|---|
| No existe fila con ese `_id` | **Crea** Lead + Activity |
| Existe y el hash del payload es idéntico | **Ignora** (sin cambios) |
| Existe y el hash cambió | **Actualiza** la cita |
| `archived: true` o `status` cancelado | **Cancela** el Lead |

> 🔑 **Lo importante:** la decisión de crear vs. actualizar **ya se toma por `_id`**, no por ningún campo de estado. Por eso `eventStatus` no cambia la lógica.

### 🔴 BUG-1 - El archivo viejo revierte la modificación *(verificado)*

**Ubicación:** `packages/Webkul/Admin/src/Services/SmdAppointmentSyncService.php:47-48`

**Qué pasa:** las modificaciones de citas **nunca llegan al CRM**. Queda el dato original.

**Por qué:** el bucle recorre los días desde el más nuevo hacia atrás:

```php
for ($i = 0; $i < $days; $i++) {
    $date = $baseDate->copy()->subDays($i)->toDateString();  // i=0 → HOY, i=1 → AYER
    $files = $this->dropbox->listFilesForDate($date);
    foreach ($files as $file) { $this->processFile($file, $summary, $onLog); }
}
```

Procesa **la carpeta más nueva primero y la más vieja al final**. Como la dedup es "el último archivo procesado gana", la secuencia real con los datos de hoy es:

1. Carpeta del **14** → `0141` (crea la cita) → `0144` (la actualiza a **17 jul**) ✅ correcto
2. Carpeta del **13** → el archivo viejo **sigue ahí** → su hash difiere del guardado → lo trata como "un cambio más" y **reaplica el payload viejo encima** → vuelve a **21 jul** ❌

**Impacto concreto hoy:** en SMD la cita `6a54f35…` está el **17 de julio**; el CRM la mostrará el **21 de julio**. Cuatro días de diferencia en una cita real.

**Por qué es traicionero:** mañana (15/07) la carpeta del 13 sale de la ventana de `--days=2` y **la cita se autocorrige sola**. El dato está mal solo durante la ventana del `--days` - el tiempo justo para que alguien lo vea mal y después no se pueda reproducir.

**Verificación:** se reprodujo con un test temporal usando un payload calcado del real (mismo `_id`, archivo CREATED el 13 + UPDATED el 14, cron con `--days=2`):

```
1. tras CREATED del 13              → "Creado 21 de Jul" | 2026-07-21 09:00
2. tras UPDATED del 14 (--days=2)   → "Creado 21 de Jul" | 2026-07-21 09:00   ← la modificación NO entra
3. cron 5 min después               → "Creado 21 de Jul" | 2026-07-21 09:00   ← sigue sin entrar
```

**Nota adicional:** dentro de un mismo día el orden es **pura suerte**. Hoy Dropbox devolvió `0141` antes que `0144` (cronológico, sale bien), pero la API de Dropbox **no garantiza ese orden**.

### 🔴 BUG-2 - Un fallo transitorio de Dropbox deja el sync muerto 3h30m *(verificado)*

**Ubicación:** `packages/Webkul/Admin/src/Services/DropboxService.php:23-48`

**Qué pasa:** si Dropbox falla **una sola vez** al renovar el token, el sync queda caído 3 horas y media, **incluso después de que Dropbox se recupera**.

**Por qué:** `token()` envuelve el refresh en `Cache::remember(..., 12600, ...)`, pero el closure **también retorna en el camino de error**:

```php
return Cache::remember(self::TOKEN_CACHE_KEY, self::TOKEN_TTL, function () {
    // ...
    if (! $refreshToken || ! $appKey || ! $appSecret) {
        return config('smd.dropbox.access_token') ?? '';   // ← línea 29: se cachea el fallo
    }
    // ...
    if (! $response->successful()) {
        Log::error('[Dropbox] Error refrescando token', ...);
        return config('smd.dropbox.access_token') ?? '';   // ← línea 41: se cachea el fallo
    }
    // ...
});
```

Cache no distingue éxito de error: guarda lo que devuelva el closure, incluido el string vacío, por 12600 segundos.

Peor: `retryWithFreshToken()` hace `Cache::forget()` y vuelve a llamar a `token()`, que **re-envenena el cache** con el mismo string vacío.

**Verificación:** con un test temporal, simulando un `500` del endpoint de token:

```
token tras fallo                      → ''
valor cacheado                        → ''
token tras recuperación de Dropbox    → ''   ← sigue vacío
```

### 🔴 BUG-3 - `listChanges()` lanza `TypeError` y pierde la notificación *(verificado)*

**Ubicación:** `packages/Webkul/Admin/src/Services/DropboxService.php:165-205`

**Qué pasa:** el webhook revienta y la notificación de Dropbox **se pierde**.

**Por qué:** el método está declarado `: array`, pero llama a `retryWithFreshToken()` **sin pasar `default:`**, así que hereda `$default = null`. Si el token sigue expirado tras el reintento, retorna `null` → PHP lanza `TypeError` en el `return`.

```php
public function listChanges(string $cursor): array
{
    $result = $this->retryWithFreshToken(function (string $token) use ($cursor) { ... });
    //                                   ↑ falta   , default: ['entries' => [], ...]
    return $result;  // ← TypeError si $result es null
}
```

`listFilesForDate` (`default: []`) y `downloadJson` (`default: null`) **sí lo pasan**. `listChanges` es el único que se olvidó.

**Impacto:** rompe `ProcessDropboxNotification::handle()` en la línea 42, **antes de guardar el cursor**. El job reintenta 3 veces, falla, y esa notificación se pierde.

if (! $physicianRaw) {

**Verificación:**

### 🔴 BUG-12 - Una cancelación que además edita el título pierde la edición *(verificado - CORREGIDO 14/07)*

**Reportado por el usuario el 14/07:** canceló la cita `6a562447af…` y en el mismo movimiento le editó el título a `"test editado"`. El CRM canceló el lead correctamente pero **se quedó con el título viejo**.

SMD manda **un solo archivo** con la cancelación y la edición juntas:

```
event-2026-07-14-1310-6a562447af…  __v=2  UPDATED  archived=false  status="CANCELED"  summary="test editado"
```

La rama de cancelación de `applyPayload()` llamaba a `cancelDropbox()` y retornaba, **sin aplicar nunca el contenido** ni guardar el `raw_payload`. Efecto secundario: `source_updated_at` avanzaba a la versión nueva mientras `raw_payload` quedaba en la vieja, dejando la fila inconsistente.

**Corregido:** la rama de cancelación ahora aplica `updateDropbox()` antes de cerrar el lead (solo si hay `activity_id`, porque sin él `updateDropbox()` crearía una cita nueva para un evento ya cancelado) y persiste el `raw_payload`.

Verificado sobre la cita real: `ACTIVITY 40922` pasó de `test` a `test editado`, conservando `stage=6`, `status=0` y `lost_reason='Cita cancelada en SMD'`.

> Los archivos `CREATED` traen el asistente completo (`type: "patient"`, `phone`, `birthday`, `age`), pero los `UPDATED` traen solo `_id`, `name`, `lastName`, `fullName` e `id`. Sin `type` no hay forma directa de saber cuál asistente es el médico y cuál el paciente; sin `phone` no se puede matchear al paciente existente.
>
> Si es un efecto colateral del cambio y pueden hidratar los `UPDATED` igual que los `CREATED`, el mapeo se simplifica mucho. Si no, lo resolvemos por nuestro lado cruzando los `_id` contra nuestra tabla de doctores.

**Decisión de diseño:** la corrección la garantiza el **descarte por `updated_at`**, no el ordenamiento. El orden por nombre de archivo es solo una optimización para evitar estados intermedios; si SMD cambia el formato del nombre, el descarte sigue protegiendo. Por eso `eventStatus` no se usa para decidir crear vs. modificar: el `_id` ya lo resuelve, y el descarte funciona incluso con los archivos legacy que no traen `eventStatus`.

`processPayload()` es ahora el único punto por el que pasan los tres orígenes del sync (comando, job del webhook, job de la UI), así que el descarte y el lock aplican a todos.

### Tests

`tests/Feature/SmdStalePayloadSyncTest.php` (nuevo, 5 tests) + 3 tests en `DropboxServiceTest.php`:

- La modificación de hoy gana sobre el archivo de creación de ayer (`--days=2`).
- El archivo viejo no revierte la cita aunque el cron corra muchas veces.
- Gana la versión más nueva aunque Dropbox devuelva los archivos en orden inverso.
- Los archivos legacy sin `updated_at` ni `eventStatus` se siguen procesando.
- Un legacy sin `updated_at` no borra la referencia guardada.
- Un refresh fallido no queda cacheado; al recuperarse Dropbox el sync vuelve solo.
- Un refresh sin `access_token` en la respuesta no se cachea.
- `listChanges` devuelve la estructura por defecto en vez de lanzar `TypeError`.
